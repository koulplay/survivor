# Урок B4. Повторяемость: хэш состояния и тест

**Коротко.** Программа повторяема (детерминирована), если одни и те же входы всегда дают один и тот же результат. Проверяют это так: запускают два прогона с одинаковыми входами и сравнивают миры. Чтобы не сравнивать поле за полем, мир сворачивают в одно число — хэш. Для этого нужно получить биты `float` без потерь (`std::bit_cast`), выбрать алгоритм (FNV-1a) и обойти ловушки: выравнивание в структурах, границы между списками, скрытые входы.

**Что строишь в шаге** (`docs/roadmap.md`, B4): тест — два мира `World(42)`, один сценарий ввода «номер тика → `Input`», по 3600 тиков, хэши сравниваются по ходу прогона. Где будет жить функция хэша и что в неё войдёт — решаешь ты; урок даёт механизм на учебном примере, а не готовый код для `World`.

---

## 1. Зачем

B3 сделал так, что логика в принципе повторяема: шаг всегда 1/60 с, ввод приходит параметром, случайные числа — из `world.rng` с зерном. «В принципе» — это пока убеждение. Тест превращает его в факт и дальше сторожит: любая будущая правка, которая сломает повторяемость (скрытый `static`, `GetTime()` в логике, неинициализированное поле), сделает тест красным в тот же день, а не через месяц, когда сломается реплей.

Кому нужна повторяемость:
- **воспроизведению багов** — зерно плюс записанный ввод дают ту же партию, баг повторяется сколько угодно раз;
- **реплеям** (этап J) — хранится зерно и ввод по тикам, а не состояние мира: пара байт на тик;
- **балансу по симуляциям** (J) — тысячи прогонов без окна, у каждого результат зависит только от зерна и стратегии;
- **сети** (раздел «Куда игра может расти» в `docs/roadmap.md`) — при lockstep по сети ходит только ввод, а рассинхрон ловят, сравнивая хэши.

**Зачем именно хэш.** Сравнить два мира можно и поле за полем. Но тест сравнивает их много раз за прогон, чтобы узнать не только «разошлись ли», но и «когда». Хэш — одно число на каждый момент: его дёшево сравнить, напечатать в сообщении теста («тик 1200: 3f2a… против 91c0…»), записать в реплей или отправить по сети.

## 2. Скрытые входы

Видимые входы игры — зерно и `Input` на каждый тик. **Скрытый вход** — всё остальное, что влияет на результат. Повторяемость ломают именно они:

| Скрытый вход | Пример | Как у нас |
|---|---|---|
| Время | `GetTime()`, `GetFrameTime()` в логике | с B3 логика получает только `kTick` |
| Случайное зерно | `std::random_device` | только в `World()`; тесты берут `World(42)` |
| Глобальное и `static`-состояние | `static std::mt19937` в функции | убрано в B2 |
| Неинициализированная память | поле без значения по умолчанию | читать такое поле — неопределённое поведение. У части полей значения по умолчанию нет (`Exp::pos`, `Bullet::vel`, …), но при создании их всегда заполняют; новое поле — сразу со значением по умолчанию |
| Адреса в памяти | сравнение `<` указателей на разные объекты | результат не задан стандартом (cppreference, «Comparison operators»). У нас `&self > &other` в `UpdateSeparation` сравнивает элементы **одного** вектора — это порядок номеров в массиве, он задан |
| Порядок обхода | `std::unordered_map` | у нас таких контейнеров нет; появятся — порядок обхода не должен влиять на логику |
| Плавающая точка | другой компилятор, флаги, процессор | см. ниже |
| Распределения `<random>` | другая стандартная библиотека | B2: у нас везде libstdc++ (P2059R0) |
| Потоки | порядок выполнения | этап J |

**Плавающая точка.** Отдельные операции IEEE 754 (`+`, `-`, `*`, `/`, `sqrt`) округляются однозначно. Но результат всё равно может зависеть от сборки: компилятор вправе переставлять и сливать операции. Например, GCC по умолчанию разрешает сливать `a * b + c` в одну инструкцию FMA (`-ffp-contract=fast`), если сборке разрешены такие инструкции процессора, например с `-march=native`; у FMA одно округление вместо двух, и последний бит может отличаться. `-ffast-math` разрешает ещё больше. Функции вроде `sin`, `cos`, `exp` из разных библиотек могут давать разные последние биты. Glenn Fiedler («Floating Point Determinism») отвечает на вопрос о повторяемости «да, если»: тот же исполняемый файл, тот же компилятор, машины той же архитектуры.

Для нашего теста это хорошая новость: оба прогона идут в одном процессе, это один и тот же исполняемый файл. Если тест покраснел — виноват наш код, а не процессор. Поэтому тест сравнивает **два прогона**, а не записанное заранее число: записанный хэш сломался бы при смене компилятора или стандартной библиотеки и после каждой задуманной правки игры.

## 3. Хэш: свернуть мир в число

Аналогия — отпечаток пальца: короткий, у одного и того же всегда одинаковый, у разных почти всегда разный. Граница аналогии: у хэша совпадения у разных входов возможны (коллизии). Для идеального 64-битного хэша вероятность, что конкретная пара разных миров совпадёт, — 1 / 2⁶⁴ ≈ 5 × 10⁻²⁰. FNV-1a не идеален, но для поиска случайного расхождения двух прогонов этого с запасом хватает (оценка Claude).

### FNV-1a

Алгоритм из RFC 9923 («The FNV Non-Cryptographic Hash Algorithm», февраль 2026):

1. Начать с числа offset basis.
2. Для каждого байта данных: `hash ^= байт`, затем `hash *= FNV prime` по модулю 2^64.
3. Вернуть `hash`.

Для 64 бит: offset basis = 14695981039346656037 (0xCBF29CE484222325), prime = 1099511628211 (0x100000001B3). RFC советует FNV-1a для общего использования: на коротких данных он перемешивает биты лучше, чем FNV-1, где те же два действия идут в обратном порядке.

FNV — **некриптографический** хэш: RFC прямо не рекомендует его там, где злоумышленник не должен суметь подобрать совпадение. Для паролей и подписей он не годится. Нам и не нужно: мы ищем случайное расхождение, а не защищаемся.

Почему тип — `std::uint64_t` из `<cstdint>`:
- **Беззнаковый**, потому что умножение переполняется на каждом байте. Переполнение беззнакового — это по правилам языка счёт по модулю 2^N, а переполнение знакового — неопределённое поведение (cppreference, «Arithmetic operators», раздел «Overflows»).
- **Ровно 64 бита на любой системе.** `unsigned long` на 64-битной Windows — 32 бита (модель LLP64), а на 64-битном Linux — 64 (LP64) (cppreference, «Fundamental types», раздел «Data models»). Тот же код с `unsigned long` считал бы на Windows и Linux разные хэши.

**Порядок байтов задаём сами.** Целое из 4 байт можно скормить хэшу байт за байтом сдвигами — сначала младший (`v >> 0`, `v >> 8`, …). Тогда порядок не зависит от процессора. Если копировать байты из памяти, порядок будет тем, в каком их хранит процессор. Windows и Linux у нас на x86-64, где порядок одинаковый, так что сейчас разницы нет, но сдвиги переносимы бесплатно.

## 4. Биты `float`: `std::bit_cast`

Хэш ест байты. У `int` взять байты просто, а у `float`? Три способа, которые приходят в голову первыми, и один правильный.

**`static_cast<std::uint32_t>(f)` — неверно.** Это преобразование **значения**: дробная часть отбрасывается. `static_cast<std::uint32_t>(100.2f)` и `static_cast<std::uint32_t>(100.7f)` — оба 100. Хэш не увидит, что враг сдвинулся на полпикселя, — а именно такие расхождения и надо ловить.

**`*reinterpret_cast<std::uint32_t*>(&f)` — неопределённое поведение.** Правило алиасинга (cppreference, `reinterpret_cast`, раздел «Type aliasing»): читать объект можно через его собственный тип, через знаковый или беззнаковый вариант этого типа и через `char`, `unsigned char`, `std::byte`. Объект `float` через `std::uint32_t` — нельзя. Это не формальность: на правиле держится оптимизация. Компилятор считает, что запись через `float*` не меняет то, что читается через `std::uint32_t*`, и не перечитывает память. У GCC это `-fstrict-aliasing`, он включён на `-O2`, `-O3`, `-Os` (документация GCC, «Optimize Options»).

Эксперимент — отдельная программа, **так писать нельзя**:

```cpp
[[gnu::noinline]] std::uint32_t Mix(float *pf, std::uint32_t *pu) {
    *pu = 1;        // запись через std::uint32_t
    *pf = 2.0f;     // запись через float: для компилятора — «другой объект»
    return *pu;     // компилятор вправе считать, что здесь всё ещё 1
}
// float x = 0.f;  Mix(&x, reinterpret_cast<std::uint32_t *>(&x));
```

GCC 13.3 на Linux (прогон Claude 17.10.2026): `-O0` — 1073741824 (это биты `2.0f`), `-O2` — 1, `-O2 -fno-strict-aliasing` — снова 1073741824. В ассемблере `-O2` функция просто возвращает константу 1. `-Wall -Wextra` при этом молчат. Debug и Release дают разный ответ — типичный признак неопределённого поведения. Предскажи, что покажет твой GCC 13.1, и проверь.

**`union` — тоже нет.** В C++ чтение не того члена `union`, который записывали последним, — неопределённое поведение. Многие компиляторы разрешают это как расширение (cppreference); GCC — прямо в описании `-fstrict-aliasing`, если читать через сам `union`. Но это уже не C++, а диалект одного компилятора.

**`std::memcpy` — можно** (так в примере на cppreference). **`std::bit_cast` — лучше всего:**

```cpp
#include <bit>
const std::uint32_t bits = std::bit_cast<std::uint32_t>(f);   // те же 32 бита, другой тип
```

- C++20, заголовок `<bit>`.
- Компилируется, только если размеры равны и оба типа тривиально копируемые (cppreference): перепутать `float` с `std::uint64_t` не выйдет — будет ошибка компиляции, а не тихая порча.
- `constexpr`, если в типах нет указателей, `union`, `volatile` и ссылок.
- Возвращает значение — не нужно заводить переменную под `memcpy`.

**Биты против значений.** `-0.f == 0.f` — истина, а биты разные: 0x80000000 и 0x00000000. NaN не равен даже самому себе. Для нашего теста биты — то, что нужно: одинаковые вычисления дают одинаковые биты, а `-0` вместо `+0` — это тоже другое вычисление, его стоит заметить.

## 5. Почему нельзя хэшировать структуру куском памяти

Соблазн: `hash(&enemy, sizeof(enemy))` — все байты разом. Не выйдет, по трём причинам.

**1. Выравнивание.** `sizeof(Enemy)` = 24, а полей — на 21 байт: `Vector2 pos` 8 + `EnemyType type` 4 + `float health` 4 + `float hit_flash_time` 4 + `bool dead` 1. После `dead` (смещение 20) компилятор добавил 3 байта, чтобы следующий `Enemy` в векторе начинался с адреса, кратного 4 (проверено на GCC 13.3, x86-64, `Vector2` как у raylib — два `float`). Значения этих байтов ничем не заданы. Два врага с одинаковыми полями могут различаться мусором в выравнивании — тест покраснеет на ровном месте, и то не всегда.

**2. Указатели.** `World` хранит врагов в `std::vector`, а сам `std::vector` внутри — это указатели на память в куче. Байты `World` — это адреса, а не враги; у двух миров адреса заведомо разные.

**3. `float` не подходит по смыслу.** Для таких проверок есть свойство `std::has_unique_object_representations_v<T>`. По cppreference, его ввели как раз чтобы узнать, можно ли хэшировать тип как массив байтов. На GCC 13.3 оно ложно для `Enemy`, `Vector2` и `float` (у `float` одно значение NaN имеет много битовых записей) и истинно для `int`, `bool` и `enum`.

Поэтому хэшируют **поле за полем** — и сами решают, какие поля.

## 6. Однозначная кодировка: длины

Хэш видит не структуру мира, а поток байтов. Если просто выписать подряд всех врагов, потом все пули, границы между списками теряются. Классический пример — списки строк: `["ab", "c"]` и `["a", "bc"]` склеиваются в одно и то же «abc». Лечение — писать **длину перед каждой частью переменной длины**: `2 "ab" 1 "c"` и `1 "a" 2 "bc"` — уже разные потоки.

У нас это значит: перед врагами — их число, перед пулями — их число и так далее. Заодно самое частое расхождение — «врагов стало на одного больше» — хэш увидит сразу.

## 7. Пример — учебный, не наш `World`

Полная программа на тип `Particle`, которого в игре нет. Сначала прочитай и **предскажи**, какие строки вывода совпадут, потом запусти (отдельная цель или онлайн-компилятор).

```cpp
// fnv_demo.cpp — отдельная учебная программа, не часть игры
#include <bit>
#include <cmath>
#include <cstdint>
#include <cstdio>
#include <vector>

struct Fnv1a {
    std::uint64_t value = 14695981039346656037ull;   // offset basis (RFC 9923)

    void Byte(std::uint8_t b) {
        value ^= b;
        value *= 1099511628211ull;                    // FNV prime; беззнаковое переполнение — по модулю 2^64
    }
    void U32(std::uint32_t v) {                       // младший байт первым — на любом процессоре одинаково
        for (int i = 0; i < 4; ++i) Byte(static_cast<std::uint8_t>(v >> (8 * i)));
    }
    void U64(std::uint64_t v) {
        for (int i = 0; i < 8; ++i) Byte(static_cast<std::uint8_t>(v >> (8 * i)));
    }
    void F32(float f) { U32(std::bit_cast<std::uint32_t>(f)); }   // биты числа, а не его значение
    void Bool(bool b) { Byte(b ? 1 : 0); }
};

struct Particle {          // учебный тип, не из игры
    float x;
    float y;
    int kind;
    bool alive;
};

void Add(Fnv1a &h, const Particle &p) {
    h.F32(p.x);
    h.F32(p.y);
    h.U32(static_cast<std::uint32_t>(p.kind));
    h.Bool(p.alive);
}

void Add(Fnv1a &h, const std::vector<Particle> &v, bool with_size) {
    if (with_size) h.U64(v.size());                   // сначала длина
    for (const Particle &p : v) Add(h, p);
}

std::uint64_t HashTwoLists(const std::vector<Particle> &a, const std::vector<Particle> &b, bool with_size) {
    Fnv1a h;
    Add(h, a, with_size);
    Add(h, b, with_size);
    return h.value;
}

int main() {
    const Particle p1{1.5f, 2.f, 0, true};
    const Particle p2{3.f, 4.f, 1, true};

    Fnv1a empty;
    std::printf("1) пустой хэш:             %016llx\n", static_cast<unsigned long long>(empty.value));

    std::printf("2) [p1] и [p2]:            %016llx\n", static_cast<unsigned long long>(HashTwoLists({p1}, {p2}, true)));

    Particle q = p1;
    q.x = std::nextafter(q.x, 100.f);                  // соседнее число float
    std::printf("3) x на одно число больше: %016llx\n", static_cast<unsigned long long>(HashTwoLists({q}, {p2}, true)));

    std::printf("4) без длин: [p1, p2] + [] = %016llx\n", static_cast<unsigned long long>(HashTwoLists({p1, p2}, {}, false)));
    std::printf("   без длин: [p1] + [p2]   = %016llx\n", static_cast<unsigned long long>(HashTwoLists({p1}, {p2}, false)));
    std::printf("   с длинами: [p1, p2] + [] = %016llx\n", static_cast<unsigned long long>(HashTwoLists({p1, p2}, {}, true)));
    std::printf("   с длинами: [p1] + [p2]   = %016llx\n", static_cast<unsigned long long>(HashTwoLists({p1}, {p2}, true)));

    std::printf("5) static_cast<uint32_t>: 100.2f -> %u, 100.7f -> %u; bit_cast: %08x и %08x\n",
                static_cast<std::uint32_t>(100.2f), static_cast<std::uint32_t>(100.7f),
                std::bit_cast<std::uint32_t>(100.2f), std::bit_cast<std::uint32_t>(100.7f));

    std::printf("6) sizeof(Particle) = %zu, полей на %zu байт\n", sizeof(Particle), 3 * sizeof(float) + sizeof(bool));
}
```

```

2) [p1] и [p2]:            27690a98ba1ae7bb
3) x на одно число больше: 23d567866f1b491e
4) без длин: [p1, p2] + [] = fc5c09cb1e9f36c1
   без длин: [p1] + [p2]   = fc5c09cb1e9f36c1
   с длинами: [p1, p2] + [] = e8339ec1cbbfecaf
   с длинами: [p1] + [p2]   = 27690a98ba1ae7bb

```

- Строка 1 — сам offset basis из RFC: байтов не было.
- Строка 3: сдвиг на самое маленькое возможное для `float` расстояние меняет хэш целиком.
- Строка 4: без длин два разных набора дают один хэш; с длинами — разные.
- Строка 5: `static_cast` не видит полпикселя, `bit_cast` видит.
- Строка 6: 3 байта выравнивания.
- Вывод совпадает с `-O0` и `-O2`, флаги `-Wall -Wextra -Wpedantic -Wconversion` молчат.
</details>

Как это соотносится с шагом: `Fnv1a` — механизм; `Add` для `Particle` и вектора — то, что тебе предстоит придумать для своих типов (`Player`, `Enemy`, пули, кристаллы…) и для самого `World`. Решения — твои: какие поля, в каком порядке, где жить этим функциям.

## 8. Тест: на что опереться

- **Сценарий ввода** — функция «номер тика → `Input`»: одни и те же номера всегда дают одинаковый ввод. Какой сценарий проверяет больше кода — решаешь ты (стоять, ходить по кругу, выбирать карточки…).
- **Состояния игры.** Прогон в тесте должен проходить `LevelUp` и `GameOver` так же, как `main`. Если просто звать `Update` 3600 раз, получится не игра. Прогон Claude на коде от 17.10: `Update` на мире в `LevelUp` переводит его в `Playing` — меню пропускается. На мире в `GameOver` тоже ставит `Playing`, а следующий вызов — снова `GameOver`: мир мигает между состояниями.
- **Числа для проверки себя.** Зерно 42, игрок стоит, в меню сразу берётся первая карточка: 6 повышений уровня и смерть на 1757-м тике (около 29 с игрового времени), дальше 1843 тика — `GameOver` (прогон Claude на коде от 17.10.2026). Подумай, проверяет ли такой сценарий то, что ты хочешь.
- **Когда сравнивать.** Только в конце — узнаешь, что миры разошлись, но не когда. Раз в 60 тиков — узнаешь секунду, с которой искать.
- **Хэш видит только то, что в него положили.** Не положил кристаллы — разница в кристаллах может «зажить» (кристалл подобран на тик раньше) и не всплыть никогда. Список «что влияет на будущее партии» — главная мысль шага.
- **Генератор.** У движков `<random>` есть `operator==`: он сравнивает внутренние состояния, и `operator<<`, который выводит состояние в поток (cppreference, `std::mersenne_twister_engine`). Сравнить генераторы двух миров можно напрямую.
- **Зелёный сразу.** На сегодняшнем коде тест, скорее всего, пройдёт с первого запуска, и это ничего не доказывает. Сломай нарочно хотя бы раз: (а) другой вход — другое зерно или другой ввод на одном тике у второго мира; (б) скрытый вход в коде — например, `static`-счётчик в функции логики. Тест должен покраснеть, и сообщение должно показать, на каком тике.
- **Второй похожий случай.** Если `switch` по состоянию из `main` придётся повторить в тесте — это второй похожий случай. Подумай, кто ещё должен уметь «прожить один тик в любом состоянии».

## 9. По желанию: `git bisect`

Как найти коммит, который сломал повторяемость, если заметил это через двадцать коммитов? Двоичным поиском по истории: git берёт середину, ты говоришь «хорошо» или «плохо», он делит пополам дальше. 16 коммитов — 4 проверки, 1000 — 10.

```
git bisect start
git bisect bad                 # текущий коммит плохой
git bisect good <хэш коммита>  # этот был хорошим
git bisect run <скрипт>        # дальше git проверяет сам
git bisect reset               # вернуться туда, где был
```

`git bisect run` понимает код возврата скрипта: 0 — коммит хороший; от 1 до 127, кроме 125, — плохой; 125 — «этот коммит не проверить», git его пропустит; другой код прерывает поиск (git-scm.com, `git bisect`, раздел «Bisect run»). Значит, скрипт собирает тесты; не собралось — выходит с кодом 125; собралось — запускает тест и возвращает его код. Сначала проверь, с каким кодом выходит тестовая программа, когда тест падает: в PowerShell — `$LASTEXITCODE`, в cmd — `echo %ERRORLEVEL%`. Скрипт можно писать на `sh` для Git Bash — он входит в Git for Windows.

Упражнение: несколько коммитов, в одном — нарочная поломка повторяемости, `git bisect run` находит его сам.

## 10. Подвохи и края — коротко

- `World()` берёт зерно из `std::random_device` — в тестах только `World(42)`.
- `std::size_t` → в хэш как `std::uint64_t`, явно: тогда хэш не зависит от ширины `size_t`.
- `enum class` → `static_cast` к целому: неявного преобразования нет.
- Порядок полей в хэше важен: хэш (a, b) ≠ хэш (b, a). Порядок выбрать один раз.
- Повторяемость — только в пределах одного исполняемого файла (Fiedler). Сравнивать хэши Windows и Linux — другая, гораздо более трудная задача, она не входит в B4.

## 11. Как рассказать на собеседовании

**Ответ на 30 секунд.** «Логика игры детерминирована: одно зерно и одна запись ввода дают ту же партию. Это проверяет тест: два мира с одинаковым зерном и сценарием ввода идут по 3600 тиков, и раз в секунду их хэши сравниваются. Хэш — FNV-1a по полям: `float` — через `std::bit_cast`, у списков — сначала длина. Структуры целиком не хэширую из-за выравнивания и указателей. Сравниваю два прогона, а не записанное число: плавающая точка повторяется только в пределах одной сборки».

Вопросы следом:
- **Что делает программу недетерминированной?** Скрытые входы — таблица из раздела 2.
- **Что такое строгий алиасинг и почему `*reinterpret_cast<std::uint32_t*>(&f)` — неопределённое поведение?** Раздел 4 и эксперимент.
- **Почему нельзя хэшировать структуру как кусок памяти?** Раздел 5.
- **Чем `std::bit_cast` лучше `memcpy`?** Проверка размеров при компиляции, `constexpr`, возвращает значение; `memcpy` тоже законен.
- **Почему `std::uint64_t`, а не `unsigned long`?** LLP64 и LP64.
- **Можно ли FNV-1a для паролей?** Нет: некриптографический.
- **Как найти коммит, который сломал тест?** `git bisect run`.
