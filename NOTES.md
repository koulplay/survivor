6. **Шаг 4. Пули удалялись по краю экрана.** За краем экрана игрок переставал стрелять; с камерой в шаге 8 это станет постоянным. *Ловить:* условие «жив ли объект» не должно зависеть от экрана. *Повтор в шаге 8.2:* граница «игрок ± полэкрана» сделала жизнь пули зависимой от направления бега: по врагу на экране в 560 пикс стоя — попадание, на бегу пуля пропадала у края. *Нашли:* симуляция без окна. *Исправлено:* у пули свой срок жизни.

## Приёмы
28. **Повторяется по кругу** (мигание, смена цвета по кругу). Время делим на длину куска и отбрасываем дробь — номер куска; остаток от деления номера на число фаз — фаза. Пример: 2,54 / 0,5 = 5,08 → 5 → 5 % 3 = 2. Дробь отбрасывать обязательно: встроенный `%` для `float` не компилируется (cppreference, «Arithmetic operators»). Тот же приём уже был в коде: `GameTimeToText` (`/ 60` — минута, `% 60` — секунда) и меню уровня (`% 3`).

## Ловушки, о которых предупреждали заранее
- Скорость и урон «в секунду» умножать на `dt` — иначе они зависят от FPS. Разовое событие (удар, попадание пули) — без `dt`, иначе от FPS зависит уже оно: удар 30 при 60 FPS превращался в 30 × 1/60 = 0,5 HP (A5).
- `for (auto e : v)` без `&` меняет копии, и компилятор молчит.
- Удаление из вектора внутри цикла по нему пропускает элементы. Помечать `dead`, а после цикла — `std::erase_if`.
- Добавление в вектор внутри цикла по нему: `push_back` при перевыделении делает итераторы и ссылки недействительными — неопределённое поведение, запуск может его не показать (cppreference, `std::vector::push_back`). Копить в отдельном векторе, вливать после цикла (задача A).
- `v[0]` у пустого вектора — неопределённое поведение. Если значения может не быть — `std::optional`.
- В C++ `(0 - 1) % 3` равно −1. Для перехода по кругу — `(i + n - 1) % n`.
- Наведение мыши перебивает клавиатуру; выбирать мышью только когда мышь двигалась.
- Генератор случайных чисел без зерна даёт одну и ту же последовательность при каждом запуске.
- Таймер, который копит время, пока цели нет, потом выдаёт очередь выстрелов. Без цели держать его на интервале.
- Быстрая пуля проскакивает врага: при 60 FPS и радиусах 3 и 10 на 1560 пикс/с пролётов не было, на 1700 — 82 из 1000.
- После точки останова `GetFrameTime()` возвращает всю паузу, поэтому `dt` ограничен.
- Тело обычной функции в заголовке даёт `multiple definition`; в каждом заголовке — `#pragma once`.
- Невиртуальный деструктор у базового класса: `-Wall -Wextra -Wpedantic` молчат, `-Wnon-virtual-dtor` ловит.
- `GetRandomValue` включает обе границы, а при `min > max` меняет их местами (raylib 6.0: `raylib.h`, `rcore.c`).
- Порядок строк таблицы видов должен совпадать с порядком перечисления: `static_assert` сверяет только число строк.
- Флаги предупреждений — у каждой цели свои: `target_compile_options(<цель> PRIVATE …)` не доходит до библиотеки, которую цель подключает; без своих флагов код библиотеки собирается молча (B1).
- `main` в статической библиотеке не даёт ошибки «два `main`»: компоновщик берёт из архива только то, чего ему не хватает, и может молча взять `main` игры вместо `main` Catch2 — тестовая программа запустит игру (B1, проверено на Linux).
- ctest ничего не собирает, а запускает уже собранное; конфигурация «All CTest» в CLion перед запуском собирает все цели, ручной `ctest` — нет (B1).
- Генератор (`std::mt19937`) — только по ссылке: копия выдаёт те же числа, что выдал бы оригинал, а оригинал не сдвигается, поэтому функция с генератором-параметром по значению каждый раз возвращает одно и то же (B2; прогон: «3 3 3 3» против «3 5 6 2»).
- Одинаковы во всех стандартных библиотеках только генераторы; распределения и `std::shuffle` — нет (P2059R0: `uniform_int_distribution(0, 100)` от `mt19937` без зерна — 53 на MSVC, 82 на libstdc++). У нас и на Windows, и на Linux — libstdc++ (B2).
- `std::uniform_int_distribution`: обе границы включены, как у `GetRandomValue`, но `a ≤ b` — предусловие, нарушение — неопределённое поведение; `GetRandomValue` перепутанные границы меняет местами сам (B2).
- Поля инициализируются в порядке объявления: поле, инициализатор которого читает другое поле (`rng{seed}`), — ниже читаемого. В Debug GCC 13 об ошибке молчит, `-Wuninitialized` — только с `-O2` (B2).
- `assert` в Release ничего не делает: там `NDEBUG` (`CMAKE_CXX_FLAGS_RELEASE = -O3 -DNDEBUG`). Он ловит ошибки программиста — например, неверный номер карточки из теста, — а не игрока (B2).
- Кадр может содержать 0, 1 или 2 тика — даже при 60 FPS: время кадра измеряется и почти никогда не равно ровно 1/60 с. «Держат» сбрасывать в конце кадра, «нажали» — после тика (B3, урок).
- `IsKeyPressed` весь кадр отвечает «да» при каждом вызове: raylib опрашивает ввод один раз за кадр, в конце `EndDrawing`. Прочитать ввод дважды за кадр — одно нажатие сработает дважды (B3; raylib 6.0, `rcore.c`).
- Событие в `bool` копить через `if (IsKeyPressed(…)) x = true;`, а не `x = IsKeyPressed(…)`: перезапись в следующем кадре теряет нажатие из кадра без тика. Величину события — сдвиг мыши — копить через `+=` (B3).
- `+=` и другие операторы для `Vector2` объявлены в `raymath.h`: без него не компилируется (B3).
- `float`-часы: 3600 × `1.f / 60.f` во `float` — 59,999256, за 15 минут отставание 0,18 с. Время — в `double` или целым счётчиком тиков (B3, прогон Claude).
- Смешение `float` и `double` видно только с `-Wfloat-conversion`: в `-Wall -Wextra` его нет (B3).
- `switch` по состоянию игры — внутри цикла тиков: состояние может смениться между двумя тиками одного кадра (B3).
